# 持久化与配置漂移

用于“修好后再次泄露”“同名订阅重新导入后失效”及跨订阅复用。不预设订阅服务商、UID、代理组名或解析器；本机修复脚本不是通用模板。

仅对实际代理配置变更使用下列生成链检查。首次检测通过且无改动时直接交付；只有浏览器设置变更时，按 [WebRTC 参考](webrtc.md) 或该浏览器支持的入口核对保存与复测，不为此重载代理配置。

## 先找到正在生效的来源

分别记录以下层次，原始值只留在私有备份中：

| 层次 | 必须核实的内容 |
| --- | --- |
| 当前订阅 | UID、源文件、当前绑定的 merge/script/rules/proxies/groups；不要只比显示名 |
| 客户端设置 | DNS 面板是否接管字段、TUN 和端口等客户端管理项、启用的内置增强 |
| 全局与订阅扩展 | 内容、执行顺序、是否为空入口、同名出站冲突、旧逻辑是否重新引入问题规则 |
| 生成配置 | 当前输出与上次已验证候选的完整语义差异，而不只是修改时间 |
| 实际运行态 | 内核加载结果、选中节点、DNS/业务连接出站；文件存在不代表已经加载 |

重新导入可以得到相同显示名但不同 UID 和空扩展。旧 profile 上保存过修复，不能证明新 profile 已受保护。自动更新、切换配置或客户端重新生成也可能覆盖手工写入的运行文件。

看到更新时间变化，只能说明元数据变化。只有生成配置确实回到旧内容或丢失已验证字段，才有配置回退证据；没有事件日志时不要断言一定是自动更新触发，更不能把它归因于另一个同时发生的浏览器设置试验。

## 持久层的选择与顺序

优先使用当前客户端支持、影响范围明确的扩展。单订阅修复不必默认改全局；跨订阅需求明确或已经反复因重新导入丢失修复时，可将已验证的共同逻辑放入全局层，但须先审查各层组合。

Clash Verge Rev v2.5.8 的增强代码先执行全局 merge/script，再执行订阅 merge/script；之后还会恢复客户端管理的字段。启用 DNS 设置且填写了相应字段时，脚本中的同名 DNS 设置可能被丢弃。因此“放到全局”不等于最终优先级最高，“两份脚本单独运行都成功”也不等于整个生成链成功。其他版本重新核对实现与生成结果。[版本实现](https://github.com/clash-verge-rev/clash-verge-rev/blob/v2.5.8/src-tauri/src/enhance/mod.rs)

复用策略须符合以下条件：

- 从当前配置发现并明确允许的代理组，核实选中节点和回退路径；不能取第一个组、硬编码旧服务商名称或默认退回 DIRECT。
- 对未知或歧义结构，保留其配置并明确报告“未应用、未验证”；或者停止本次部署并要求重新审查。不得把跳过称为保护成功。
- 已有 sniffer（包括显式禁用）、fake-IP 过滤模式、同名出站、其他扩展逻辑出现冲突时，在构造结果前拒绝或明确合并。不是把 `enable: false` 当成可覆盖的空配置。
- 每个可能写入这些字段的扩展都做预检；不能只保护全局层、任由后执行的订阅脚本覆盖。优先维护一份策略来源；若客户端需要两层同时应用，验证其组合和幂等，并记录后续同步责任。

**脚本拒绝不等于阻断网络。** v2.5.8 的 `use_script` 在异常时记录日志并返回输入配置，客户端可能继续生成原配置。`throw` 只能避免该脚本覆盖不兼容输入，不能当成防泄露的断网开关。出现跳过、异常或被设置面板覆盖时，核查最终配置和运行态，不报告“安全生效”。[异常处理实现](https://github.com/clash-verge-rev/clash-verge-rev/blob/v2.5.8/src-tauri/src/enhance/script.rs)

## 从已验收候选到持久结果

先保留已在目标浏览器通过 DNS/WebRTC 双项验收的候选，再做持久化；只有触发国内兼容分支时，才另需原失败业务成功的确认。不要在保存过程中加入未经测试的优化。

1. 写入前重读当前 UID、扩展绑定、将写文件和受保护字段。哈希变化时先检查差异；不得为让检查通过而直接更新基线。只可在证据支持时忽略指定的非语义时间字段，不能忽略整个订阅元数据文件。
2. 若运行文件被还原为已备份的旧基线，可以重新验证同一候选并修复持久来源；若有任何无关变化，先保留并合并，不能套用整份旧配置。
3. 能可信离线重放时，按实际生成顺序执行所有相关层，包括客户端拥有的字段。校验输出等于已验收候选、重复运行幂等、冲突时输入未被修改、未知结构没有被擅改。无法重放完整链时标记离线组合未测，改用客户端支持的预览或重新生成取得最终产物，与同阶段候选比较。Node 中的脚本检查不代表客户端内嵌引擎或完整生成链已验证。
4. 在实际内核上做配置语法校验；用既有受保护接口加载。热加载本身不会执行客户端扩展，也不能替代 GUI 重新生成测试。
5. 在不打断用户工作的前提下验证重新生成，再分别验证重启、订阅更新或切换回来中与复发相关的一项。没有执行的场景明确标记未测，不为补测试强行重启已恢复的应用。
6. 持久化后在同一目标浏览器重新完成 [两项验收](acceptance.md)，检查 DNS/UDP 出站；若最终配置不同，补做受影响项目，兼容分支涉及的真实业务也须复验。

运行脚本和断言时捕获诊断输出，只回报脱敏结论；深度比较失败的原始异常可能包含整份节点配置。不要把完整对象、控制器凭据或原始 stderr 直接写进对话/公开测试报告。

使用严格离线比较核对两份完整的同阶段配置副本：

```sh
python scripts/audit_mihomo.py /private/path/verified.json --compare /private/path/regenerated.json --require-equivalent
```

普通 `--compare` 只审查保留项，允许 DNS/sniffer/新增节点留待人工复核；它不能证明持久化等价。`--require-equivalent` 会比较所有字段，保留 DNS 内映射和列表顺序；仍不证明实际加载或网络可用。详情见 [辅助脚本](helper-tools.md)。

## 交付与回滚

记录验证矩阵：语法、脚本组合、幂等、运行热加载、目标浏览器 DNS/WebRTC、客户端重新生成、重启、订阅更新/切换，各自标注已测或未测；真实业务仅在兼容分支触发时要求，不适用时写明未触发。不要用一项通过概括全部。

备份与恢复只涉及本次改动的文件/字段。回滚前确认当前 UID 和配置未被后续修复改变；不一致时停止整份恢复，按差异处理。公开仓库仅发布通用步骤和合成测试，不能提交源订阅、运行配置、manifest 中的个人路径/UID、原始日志或凭据。
