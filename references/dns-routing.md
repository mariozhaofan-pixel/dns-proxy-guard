# DNS 路由与保护边界

核对日期：2026-10-12。本文区分通用网络原理与版本实现；涉及字段语义的实现依据为 **Mihomo v1.19.32**。其他内核或版本须重新核对官方文档、配置校验结果与实际流量，不能直接套用整段配置。

## 先约定保护目标

| 模式 | 约定 | 可以怎样报告 |
| --- | --- | --- |
| strict-proxy DNS | 约定范围内的公网域名查询只允许经代理到指定解析器；审计浏览器、应用及引导解析 | 在已验证的应用、协议和时间范围内，查询未绕过指定代理路径 |
| split encrypted DNS | 代理业务的 DNS 经代理；获准直连业务使用指定的直连加密 DNS | DNS 按分流使用加密解析；**不能称为全部 DNS 经代理** |

先确认采用哪一种。企业内网域名、代理节点域名的引导查询如有例外，单列其范围、解析器和传输路径；存在例外时不要承诺“全部 DNS 都走代理”。不能以“改善国内 CDN”为由静默把严格模式改成分流模式。

DoH 加密客户端到解析器的一段通信，解析服务仍可看到查询及其连接来源；直连 DoH 通常暴露本地出口，代理 DoH 通常暴露代理出口。它不等于匿名，也不保证所有应用遵循该解析器。[RFC 8484 隐私讨论](https://www.rfc-editor.org/rfc/rfc8484.html#section-8)

## 分清五条解析路径

| 路径 | Mihomo 中的相关入口 | 排查重点 |
| --- | --- | --- |
| 普通域名查询 | `nameserver`、`fallback`、`nameserver-policy` | 检查每个上游的实际出站，包含备用服务器 |
| 解析器自身的域名 | `default-nameserver` | 这是引导解析；不能遗漏或产生循环依赖 |
| 代理节点的域名 | `proxy-server-nameserver` | 代理建立前如何解析节点；直连例外须明确 |
| 已选定 DIRECT 的连接 | `direct-nameserver` | 检查连接元数据是否仍有域名，以及重新解析使用的策略 |
| 浏览器或应用自己解析 | 浏览器 DoH、应用 DoH/HTTPDNS、缓存 | 可能完全不经过内核的 DNS 模块；单独观察其网络连接 |

`respect-rules: true` 只表示 DNS 连接遵循路由规则；规则仍可能选择 DIRECT。指定解析器的代理后缀时，核实名称存在、实际选择及故障回退行为。不得凭空填写代理组名，也不要以关闭证书验证解决 DoH 连接错误。[DNS 字段与出站参数](https://wiki.metacubex.one/config/dns/)

## 分流解析的必要限制

- `direct-nameserver` 可为直连连接提供更合适的解析结果；`direct-nameserver-follow-policy: false` 时不继承普通 `nameserver-policy`。因此仅在普通策略中抑制 AAAA，并不保证 DIRECT 再解析也抑制 AAAA。
- 重新解析需要域名元数据。已经只剩字面 IP 的连接，不能假定内核仍知道原始域名。TCP、UDP 和不同映射模式应分别测试。[DIRECT 实现](https://github.com/MetaCubeX/mihomo/blob/v1.19.32/adapter/outbound/direct.go)
- DNS 的域名策略与连接的最终路由不是同一判断。把一整个地域域名集交给直连解析器，可能把本来要求代理访问的域名也交给该解析器。
- v1.19.32 的策略构建保留顺序，地理或规则集匹配可能先于后面的具体域名匹配；不能假定“更具体的一项永远优先”。调整后用实际命中证据验证，并检查 GUI 生成结果中的顺序。[解析器策略与独立 DIRECT 解析器](https://github.com/MetaCubeX/mihomo/blob/v1.19.32/dns/resolver.go)、[配置解析](https://github.com/MetaCubeX/mihomo/blob/v1.19.32/config/config.go)

## 不把开关当作证明

- TUN 的 DNS 劫持针对配置匹配到的 DNS 流量。UDP 53 与 TCP 53 应分别核对；端口 53 劫持无法自动接管 HTTPS 中的 DoH 或应用 HTTPDNS。后者需要识别实际连接及其出站，不能仅靠开放一个劫持开关。[Mihomo TUN 文档](https://wiki.metacubex.one/config/inbound/tun/)
- `fake-ip` 是域名映射方式，不是所有设备必需的防泄露开关。已有正常 `redir-host` 或其他方案时，不要为“优化 DNS”直接全局切换；对真实 IP 的应用例外必须由兼容性证据支持。[Mihomo DNS 模式](https://wiki.metacubex.one/config/dns/)
- 浏览器安全 DNS 是否违背目标，取决于请求走哪条网络路径、选择哪个解析器，以及失败时是否回退。既不能默认“开着必泄露”，也不能默认“关了必安全”。需要统一交给代理 DNS 时，可做单浏览器的可回滚试验，并验证实际流量。[Chrome 安全 DNS](https://support.google.com/chrome/answer/10468685)、[Firefox DoH 等级](https://support.mozilla.org/en-US/kb/dns-over-https)
- 清理缓存只能移除旧结果，不能修正路由。系统、浏览器、内核、应用 HTTPDNS 可能各有缓存；记录清理了哪一层，不将一次新结果误当持久修复。

## 验证与报告

1. 记录系统、客户端与内核版本，以及当前代理模式、DNS 上游、TUN 状态、应用进程和子进程。导出结果先脱敏，不打印节点凭据或控制器令牌。
2. 对选定测试域名分别查询 A、AAAA；记录返回值、时间、缓存状态及对应解析器。使用获准的测试域名，避免把私人域名发往公共测试服务。
3. 触发目标应用的实际动作，核对域名或 IP、进程、命中规则、出站和失败阶段。一次 DNS API 查询成功，只证明该查询路径可用；不能替代 DIRECT 再解析和应用测试。
4. 需要证明传输路径时，在获准范围内观察物理接口与代理连接，覆盖 IPv4/IPv6、TCP/UDP 53、已知加密解析端点及备用路径。只看到“没有 UDP 53”不足以排除其他路径。
5. 浏览器泄露页只是一组浏览器测试查询。解析器所在地也不等于用户出口所在地。结合连接记录或抓包，报告“本次测试未发现某类绕行”，不要扩大成永久、全应用的保证。

验证表至少包含：保护模式、测试应用与动作、观察时间、解析器、实际出站、IPv4/IPv6、结果、未覆盖范围。需要回滚时恢复本次改动，不重置整机网络。
